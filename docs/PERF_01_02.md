# PERF-01/02: latency and guardrails on the PERF01 branch

## What changed

This implementation extends API-04's **existing** `/api/v1/metrics` response.
It preserves the names and behavior of:

- `sayangcare_http_requests_total` (also used by request-rate HPA)
- `sayangcare_http_requests_by_status_total`
- `sayangcare_http_request_duration_seconds`

PERF collectors use `prometheus` 0.14 and append their output through the same
exporter. HTTP instrumentation is not replaced. API-04's current HTTP histogram
is aggregate and stops at a one-second finite bucket; PERF's stage histogram has
longer buckets for bounded AI waits. This does not claim route/method labels or
active-call metrics have been added to API-04.

**No Kubernetes manifest, replica count, HPA limit, or per-pod database pool
setting is changed.** The prior implementation's pool adjustment was a change
to PostgreSQL connections per API pod, not to the number of pods.

Existing FIX-01 archival recovery and TEST-04 scripts remain unchanged. FIX-03
continues storing alerts in PostgreSQL. A fallible `try_record_alert` variant is
used for timed turn writes; existing callers retain the best-effort `record_alert`
wrapper and its logging behavior.

## Timing boundaries

PERF measures JSON `/api/v1/calls/{sid}/turn` and signed `/twilio/gather`.
`total` spans service invocation through extraction/authentication to response
creation. It excludes phone transport, speech recognition, audio playback,
response-body transmission, and client/Ingress network time. The absolute
deadline starts at handler entry; slow request uploads before extraction are
outside that application deadline. CPU stalls and OS scheduling are not hard
real-time guarantees.

Stages separately cover session read/write (including any tiered PostgreSQL
recovery), PostgreSQL operator-alert writes, escalation queueing, breaker
lookup/admission/completion, sentiment scoring, and reply generation. Absent
stages are skipped work. Total also includes uninstrumented CPU/serialization.
Do not add/subtract percentiles to derive component shares. For mean per-turn
contribution use a stage's `_sum` divided by total-turn `_count`; stage `_sum`
divided by stage `_count` is the mean of executed invocations.

## Configurable bounds

All variables below use prefix `SAYANGCARE__PERFORMANCE__`:

| Suffix | Default | Purpose |
|---|---:|---|
| `RESPONSE_BUDGET_MS` | 5000 | One absolute handler deadline |
| `PERSISTENCE_RESERVE_MS` | 1000 | Time reserved after the AI cutoff for session saving |
| `SENTIMENT_TIMEOUT_MS` | 800 | Sentiment operation cap |
| `REPLY_TIMEOUT_MS` | 3000 | Reply operation cap |
| `COORDINATION_TIMEOUT_MS` | 200 | Breaker/alert/queue operation cap |
| `MAX_AI_TURNS` | 8 | In-flight AI turns per API process, shared across Actix workers |

Each stage also observes the remaining overall budget. Alert and queue work are
best effort with a short cap; they cannot consume the session persistence
reserve. Their errors/timeouts are logged and measured. This preserves the
existing failure behavior rather than falsely acknowledging durable alerts.
An alert timeout is not retried through a new outbox; a database operation may
already have committed remotely when its local future is cancelled. Inspect
stored session/alert state before replaying timed-out work. This change does not
provide exactly-once turns or a transaction spanning Redis, queue, and alerts.

No semaphore wait queue is introduced. Overload rejects AI admission immediately,
before a breaker permit is reserved, and returns CB-03 audio fallback. The
RAII slot is released on completion/timeout/cancellation. Limits are per process,
not a cluster-wide provider quota: 20 replicas with eight slots can permit 160
AI turns plus rollout overlap. Remote providers may continue processing a
cancelled HTTP request.

Sentiment failure/timeout clears stale sentiment, records a failure against the
sentiment breaker, and still attempts a reply with deterministic risk severity
if time remains. Reply timeout/failure, exhausted budget, overload, or reply
breaker rejection returns holding audio while preserving speech gathering.
Acquired recovery probes are completed as failures on timeout; breaker recording
has its own bounded cleanup interval. If Redis completion/acquisition is
unavailable or cancelled after remote execution, the existing shared probe lease
bounds orphan lifetime. Separate sentiment/reply breakers and generation checks
remain intact. High-risk/already escalated sessions bypass AI admission and
continue through safety response, shared alerts, queueing, and persistence.
No-key deterministic replies remain available.

The limits are initial operational choices, not live-provider SLAs. Controlled
mock runs validate timely fallback; real-provider quality/latency and Kubernetes
load/scaling results are needed before final tuning. Provider HTTP timeout is a
secondary safeguard, rather than two independent 12-second caller waits.

## Reproduce locally

Run from this checkout, with a local test PostgreSQL/Redis environment configured
in `.env`. Existing services may already be running; don't start a conflicting
second Compose project on the same published ports.

Windows:

```powershell
cargo test --locked --workspace
cargo check --locked --workspace --all-targets
cargo build --locked -p sayangcare-api --target-dir target/perf-validation
python scripts/perf-benchmark.py --output artifacts/perf
```

On this workstation, if `python` is a Windows Store alias, use:

```powershell
& 'C:\Users\engli\AppData\Local\Programs\Thonny\python.exe' scripts/perf-benchmark.py --output artifacts/perf
```

macOS:

```bash
cargo test --locked --workspace
cargo check --locked --workspace --all-targets
cargo build --locked -p sayangcare-api --target-dir target/perf-validation
python3 scripts/perf-benchmark.py --output artifacts/perf
```

The isolated build avoids replacing a normal API executable that may be running.
The stdlib-only benchmark launches its own API child on port 18091 and localhost
OpenAI-compatible mock. It refuses to reuse an occupied API port, overrides
provider keys with dummy values, and never calls phones. It uses Redis DBs
10..14 exclusively and unique breaker prefixes; do not share those DBs with
another workload. It does not flush Redis or edit `.env`. PostgreSQL test
archives and Redis synthetic sessions are retained. Child logs are ignored by
Git. All callers are synthetic. Use isolated services if existing data must
remain pristine.

Five separate runs measure deterministic/no-AI, healthy mock AI, slow sentiment,
slow reply, and overload. Each validates transcript contents/counts and durable
archive reads. Signed local Twilio smoke checks run after measurement snapshots
to check incoming Open fallback, high-risk AI bypass, alert persistence, and
completion callbacks. Outputs include per-call JSON, per-stage means, raw
Prometheus snapshots, and a summary. No-AI/mock results are not real AI evidence.

Optional controlled real AI test (three sequential synthetic turns, uses API
credits and Redis DB 15):

```powershell
python scripts/perf-benchmark.py --real-ai --output artifacts/perf-real
```

The test uses configured real credentials, checks that a model stage was actually
attempted, and never invokes real Twilio dispatch. Keep artifacts separate.
Judge fallback frequency and reply quality as well as latency.

## Pool capacity without changing pods

Read actual primary capacity, then run the read-only check:

```powershell
$primaryPod = kubectl get cluster sayangcare-db -n sayangcare -o jsonpath='{.status.currentPrimary}'
kubectl exec -n sayangcare $primaryPod -- psql -U postgres -d postgres -Atc 'SHOW max_connections'
./scripts/check-pool-capacity.ps1 -DatabaseMaxConnections 100
```

Replace 100 with the observed limit. The script reads the deployed HPA, pool
configuration/explicit environment override, and rollout surge. Defaults reserve
16 connections for other clients and allow one extra terminating pod; adjust
these assumptions to the workload. It fails rather than silently approving an
oversubscribed budget. HPA does not eliminate database capacity constraints.

For example, HPA maximum 20, pool 4, rollout surge 1, terminating allowance 1,
and reserve 16 require `(20 + 1 + 1) * 4 + 16 = 104`. A database limit of 100
would fail that conservative check. Projecting pool 3 gives 82:

```powershell
./scripts/check-pool-capacity.ps1 -DatabaseMaxConnections 100 -ProposedPoolPerPod 3
```

This is a projection only. No pool size, HPA, replica count, or cluster setting
is changed by these scripts or this implementation. Coordinate any actual
configuration adjustment with the deployment owner; rerun after rollout and
observe pool occupancy, timeouts, and latency under TEST-05 load. Additional
terminating pods or clients can require more headroom.
